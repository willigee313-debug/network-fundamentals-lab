# 08장 모범 답안 — 전체 명령 실행 기록

> 4포트 증상 채집 → 패킷 지문 3종 → 수정까지 전체 실행 기록.
> **의도 → 실측 결과 → 해석** 3단. 실측: 2026-07-12 · macOS + Docker Desktop (`clab.sh`)

## 0. 배포
```sh
./clab.sh deploy 08-tcp-3way/08-tcp-3way.clab.yml   # → cli, fw, srv running (포트 4개=증상 4종 장전)
```

## 단계 A — 4개 포트 두드리기 (증상 + 소요 시간)
**의도**: 같은 서버의 포트 4개를 같은 명령으로 두드려 **에러 메시지와 소요 시간**만으로 1차 분류.
`time`을 붙이는 것이 요점 — "몇 초 만에 실패했나"는 공짜 정보다.
```sh
for port in 6060 8080 9090 7070; do time nc -zv -w 5 10.8.2.10 $port; done
```
```
:6060  succeeded!            real 0m0.001s
:8080  timed out             real 0m5.009s    ← 5초를 꽉 채우고 실패
:9090  Connection refused    real 0m0.001s    ← 즉시 실패
:7070  Connection refused    real 0m0.001s    ← 9090과 겉보기 동일
```
**해석**: 이미 두 부류로 갈렸다 — **기다리다 죽음**(8080: 응답이 아예 없음) vs
**거절당해서 즉시 죽음**(9090/7070: 누군가 응답은 함). "빨리 실패"가 차라리 좋은 신호인 이유:
응답 주체가 존재한다는 뜻이므로 수색 범위가 좁다.

## 단계 B-1 — 정상 3-way 읽기 (:6060, 기준선)
**의도**: 실패를 읽으려면 성공의 모양부터. 플래그 순서를 몸에 새긴다.
```sh
docker exec clab-08-tcp-3way-cli tcpdump -nli eth1 tcp port 6060   # 켜두고 nc
```
```
Flags [S]  →  Flags [S.]  →  Flags [.]
(SYN)         (SYN-ACK)       (ACK — 연결 성립)
```
**해석**: `[S]`/`[S.]`/`[.]` 3연타가 정상 핸드셰이크. 이후 모든 장애 판독은 "이 3연타의
어디가, 어떻게 깨졌나"로 환원된다.

## 단계 B-2 — 타임아웃의 지문 (:8080)
**의도**: 5초 동안 실제로 무슨 일이 있었는지 — 침묵의 내용을 본다.
```sh
docker exec clab-08-tcp-3way-cli tcpdump -nli eth1 tcp port 8080   # 켜두고 nc
```
```
11:01:22.04  Flags [S], seq 2303791963      ← 최초 SYN
11:01:23.07  Flags [S], seq 2303791963      ← ~1초 뒤, 같은 seq로 재전송
11:01:24.09  Flags [S], seq 2303791963      ← 또. 상대 패킷은 전무
```
**해석**: 판독 포인트 두 가지 — ① **seq가 전부 동일** = 새 시도가 아니라 같은 연결의 재전송,
② **상대 방향 패킷이 0개** = SYN이 어딘가에서 조용히 폐기되는 중(여기선 fw의 DROP).
05장 블랙홀과 같은 "조용한 실패" 계열 지문의 TCP 버전.

## 단계 B-3 — refused 두 개 가르기: RST의 TTL (:9090 vs :7070)
**의도**: 단계 A에서 똑같아 보였던 두 refused의 **발신자**를 가른다. `-v`로 TTL을 캡처.
```sh
tcpdump -vnli eth1 tcp port 9090   # / 7070 도 동일하게
```
```
:9090의 RST → ttl 63      ← srv가 만들어 fw를 한 홉 지나며 1 깎임 = 진짜 srv의 거절
:7070의 RST → ttl 64      ← 홉을 안 지났다 = fw가 srv인 척 쏜 것 (REJECT 정책)
```
**해석**: 두 RST 모두 소스 IP는 10.8.2.10(srv)이라 주장하지만 TTL이 거짓말을 못 한다.
64에서 출발한 패킷이 홉당 1씩 깎이므로, **63 = 한 홉 건너옴(진짜), 64 = 옆에서 만들어 냄(중간자)**.
실무 번역: refused 티켓에서 서버팀만 잡지 말 것 — 중간 방화벽의 REJECT일 수 있다.

## 단계 C — 수정 + 판정 (fix.sh)
**의도**: 각 증상은 **자기 계층의 수정**이 필요함을 확인 — fw 규칙 해제(8080/7070) + 리스너 기동(9090 등).
```sh
./08-tcp-3way/fix.sh
```
```
:6060 succeeded / :8080 succeeded / :9090 succeeded / :7070 succeeded
```
**해석**: 참고로 fw 규칙만 풀면 :8080은 "타임아웃 → **진짜 refused**"로 증상이 **진화**한다
(SYN이 이제 srv까지 가는데 리스너가 없으므로). 고장이 계층에 겹쳐 있으면 하나 고칠 때마다
다음 지문이 드러난다 — "고쳤는데 에러가 달라졌어요"는 전진이다.

## 정리
```sh
./clab.sh destroy 08-tcp-3way/08-tcp-3way.clab.yml
```
**이 장의 판정 요약**: time+에러문구로 1차 분류 → 타임아웃은 "같은 seq SYN 반복+무응답",
refused는 RST의 **TTL**로 발신자 감별(63=진짜, 64=중간자).
