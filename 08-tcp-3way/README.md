# 08장. TCP 3-way 실패 유형 구분 — 증상이 원인을 말해준다

> 여기서부터 Transport 계층이다. "연결이 안 돼요"는 사실 **여러 다른 고장의 뭉뚱그린 표현**이고,
> 실패의 **모양**(타임아웃? refused? 몇 초 걸렸나?)만 읽어도 원인의 계층을 크게 좁힐 수 있다.
> 이 장은 같은 서버의 4개 포트에 4가지 운명을 심어두고, 그 지문을 채집한다.

## 0. 학습 목표
- 정상 **3-way 핸드셰이크**(SYN → SYN-ACK → ACK)를 tcpdump로 읽기
- 실패 3종의 지문: **타임아웃**(SYN 재전송) / **refused**(RST) / **중간자 RST**
- `time` + 에러 메시지 + tcpdump만으로 **원인 계층을 좁히는** 진단 습관
- 심화: RST의 **TTL**로 "누가 보낸 RST인지" 가려내기

---

## 1. 개념

### 1-1. 3-way 핸드셰이크
```
cli ──SYN──▶ srv        "연결 열자"
cli ◀─SYN-ACK── srv     "그래, 나도 준비됨"
cli ──ACK──▶ srv        "확인" → ESTABLISHED
```
- 실패는 반드시 이 3단계 중 하나에서 일어난다. **어느 단계에서, 어떤 형태로** 실패했는지가 지문.

### 1-2. 실패의 세 가지 지문
| 증상 | 걸리는 시간 | 패킷 레벨 | 뜻 |
|---|---|---|---|
| **타임아웃** | 수 초~수십 초 | SYN만 반복 (응답 없음) | SYN이 버려짐: 경로 유실 / 방화벽 DROP / 리턴 불가 |
| **Connection refused** | 즉시 | SYN → **RST** | 목적지까지 갔는데 **포트가 닫힘** (혹은 누가 RST를 쏨) |
| **연결 후 멎음/리셋** | 가변 | 데이터 중 RST/무응답 | 상태형 장비의 세션 드랍 등 (09·11장) |

- 핵심 감각: **"빨리 실패"는 오히려 좋은 신호**(누군가 응답은 한다), **"느리게 실패"가 수색 범위가 넓다**.

## 2. 토폴로지
```
   cli ──────── fw ──────── srv(10.8.2.10)
 10.8.1.10    (nftables)     :6060 정상 리스너
                             :8080 fw가 DROP        ← 장전된 고장 1
                             :9090 리스너 없음        ← 장전된 고장 2
                             :7070 fw가 REJECT(tcp-reset) ← 장전된 고장 3
```

## 4. 실습 A — 4개 포트 두드려보기 (증상 채집)

```sh
for port in 6060 8080 9090 7070; do
  docker exec clab-08-tcp-3way-cli bash -c "time nc -zv -w 5 10.8.2.10 $port"
done
```
✅ 실측:
```
:6060  succeeded!            real 0m0.001s   ← baseline
:8080  timed out             real 0m5.006s   ← 5초를 꽉 채우고 실패
:9090  Connection refused    real 0m0.001s   ← "즉시" 실패
:7070  Connection refused    real 0m0.001s   ← 9090과 똑같아 보인다?
```
**해설**: 에러 메시지와 소요 시간만으로 이미 두 부류로 갈린다 — **응답이 없어서 기다리다 죽음**(8080)
vs **거절 응답을 받고 즉시 죽음**(9090/7070). 다음 단계: 패킷으로 확정.

## 5. 실습 B — tcpdump 지문 채집

### B-1. 정상 3-way (:6060)
```sh
# (터미널1) docker exec clab-08-tcp-3way-cli tcpdump -nli eth1 tcp port 6060
# (터미널2) docker exec clab-08-tcp-3way-cli nc -zv 10.8.2.10 6060
```
✅ 실측:
```
10.8.1.10.50840 > 10.8.2.10.6060: Flags [S]  seq 2425117719          ← SYN
10.8.2.10.6060 > 10.8.1.10.50840: Flags [S.] seq ..., ack 2425117720 ← SYN-ACK (ack = 상대 seq+1)
10.8.1.10.50840 > 10.8.2.10.6060: Flags [.]  ack 1                   ← ACK, 연결 성립
```

### B-2. 타임아웃 (:8080) — 응답 없는 세계
✅ 실측 (tcp port 8080):
```
22:07:22.29  Flags [S], seq 3079874776    ← 최초 SYN
22:07:23.34  Flags [S], seq 3079874776    ← ~1초 뒤 재전송 (seq가 같다 = 같은 시도)
22:07:24.36  Flags [S], seq 3079874776    ← 또
22:07:25.39  Flags [S], seq 3079874776    ← 또... 오직 SYN뿐, 어떤 응답도 없다
```
**해설**: **같은 seq의 SYN만 반복**되고 상대편 패킷이 하나도 없다 = SYN이 어딘가에서 **조용히**
버려지고 있다(fw의 DROP). 05장의 블랙홀과 같은 부류의 지문 — "조용한 실패는 수색이 길다."

### B-3. refused (:9090) vs 중간자 RST (:7070) — 같은 에러, 다른 범인
`tcpdump -v`로 TTL까지 캡처 (✅ 실측):
```
:9090 → SYN(ttl 64) 발신 → RST 수신: ttl 63, src 10.8.2.10
:7070 → SYN(ttl 64) 발신 → RST 수신: ttl 64, src 10.8.2.10
```
**해설**: 두 RST 모두 소스는 10.8.2.10(srv)이라고 주장한다. 그러나 —
- **:9090의 RST는 ttl 63**: srv(초기 64)가 만들어 fw를 한 홉 지나며 1 깎임 = **진짜 srv의 거절** (포트 닫힘)
- **:7070의 RST는 ttl 64**: 홉을 안 지났다 = **fw가 srv인 척 만들어 쏜 것** (REJECT 정책)
- 실무 번역: refused가 났다고 서버 담당자만 잡지 마라 — **중간 방화벽의 REJECT일 수 있다.** TTL(그리고 응답 도착 시간)이 증인이다.

## 6. 수정 (fix.sh) — 계층별로 고치면 증상이 "진화"한다
이 장의 목적은 분류이므로 수정은 부록이지만, 흥미로운 실측 하나:
```sh
docker exec clab-08-tcp-3way-fw nft flush chain ip fw forward     # fw 계층만 수정하면?
```
✅ 실측: `:8080 → refused` — 타임아웃이 **진짜 refused로 바뀐다!** (SYN이 이제 srv까지
가는데, 거기엔 리스너가 없으므로.) 고장이 여러 계층에 겹쳐 있으면 **하나를 고칠 때마다
증상이 다음 지문으로 진화**한다. "고쳤는데 에러가 달라졌어요"는 후퇴가 아니라 전진이다.
```sh
# 서버 계층까지 수정 (리스너 기동)
docker exec -d clab-08-tcp-3way-srv socat TCP-LISTEN:8080,fork,reuseaddr SYSTEM:'echo pong'   # 9090/7070도 동일
```
✅ 최종 판정 (실측): 4개 포트 모두 `succeeded`.

## 7. 정리 / 교훈 — 증상 → 수색 범위 매핑

| 관찰 | 1차 결론 | 수색 범위 |
|---|---|---|
| 타임아웃 + SYN만 반복 | 패킷이 조용히 소실 | 경로(04·05장) / 방화벽 DROP / 리턴 경로(11장) |
| 즉시 refused + RST ttl에 홉 흔적 | 목적지 도달, 포트 닫힘 | 서버 프로세스/포트 (netstat) |
| 즉시 refused + RST ttl이 안 깎임 | 중간 장비의 명시적 거절 | 방화벽 REJECT 정책 |
| 연결은 되는데 이후 죽음 | 상태/세션 문제 | 09장(conntrack)·11장(대칭성) |

- **"몇 초 걸려 실패했나"는 공짜 정보다.** time을 붙이는 습관.
- 같은 에러 문자열도 패킷 레벨 지문은 다르다 — 진단의 최종 심급은 tcpdump.

## 8. 치트시트
| 목적 | 명령 |
|---|---|
| 포트 두드리기(시간 포함) | `time nc -zv -w 5 <IP> <port>` |
| 3-way 관찰 | `tcpdump -nli eth1 tcp port <p>` |
| TTL까지 관찰 | `tcpdump -vnli eth1 tcp port <p>` |
| 서버측 리스너 확인 | `ss -tlnp` |
