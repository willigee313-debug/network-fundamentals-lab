# 13장. 터널/오버레이 MTU — 커널은 자기 링크만 안다

> 07장에서 커널이 vxlan MTU를 알아서 1450으로 깎는 걸 봤다(50B 세금 자동 계산).
> 그럼 끝난 얘기 아닌가? — 아니다. **커널의 자동 계산은 "자기 링크"까지만이다.**
> 경로 *중간*의 더 좁은 구간은 VTEP이 알 길이 없고, 그 간극을 조용한 단편화가 메우다가,
> 조각을 거부하는 장비(흔하다!)를 만나는 순간 **큰 패킷만 죽는** 12장의 유령이 오버레이에서 부활한다.

## 0. 학습 목표
- 커널의 자기방어: vxlan MTU 자동 계산(로컬 underlay − 50)과 **초과 설정 거부(EINVAL)**
- 그 방어의 한계: **경로 중간의 협곡**은 반영되지 않는다
- **숨은 단편화**를 와이어에서 관찰하고, 조각 거부 환경에서의 사망 재현
- 오버레이 MTU는 "경로 최솟값 − 오버헤드"로 **사람이 설계**해야 한다는 것

---

## 1. 개념

### 1-1. 두 층위의 MTU 지식
| 누가 | 아는 것 | 모르는 것 |
|---|---|---|
| 커널(VTEP) | 자기 underlay 링크 MTU → vxlan MTU 자동 = −50 | **경로 중간**의 더 좁은 링크 |
| 12장의 TCP MSS | 양 끝의 링크 | 경로 중간 (그래서 PMTUD가 필요했다) |

같은 구조의 문제가 한 층 위에서 반복된다. **"양 끝만 아는 지식"은 경로를 보증하지 않는다.**

### 1-2. 숨은 단편화와 조각 거부
- outer UDP에는 기본적으로 DF가 없다 → 협곡을 만난 라우터는 outer를 **조각내서** 통과시킨다.
  당장은 동작한다(성능 저하만). 그래서 **아무도 모르는 채 단편화에 의존**하게 된다.
- 그런데 실무의 많은 방화벽/보안장비/호스트는 **비선두 조각(non-initial fragment)을 버린다**
  (L4 헤더가 없어 검사 불가 → 정책상 drop). 그 순간 큰 패킷만 조용히 사망한다.

## 2. 토폴로지
```
   vtep1 ──1500── r1 ──[1400]── vtep2(조각 거부)
     └ vxlan100: 자동 1450 ─ ─ ─ 자동 1350 ┘     overlay 192.168.100.0/24
```
- vtep2는 협곡(1400)이 **자기 링크**라 1350으로 자동 계산. **vtep1은 1450 — 협곡을 모른다.**
- 장전된 고장: vtep2가 와이어 쪽(eth1) 비선두 조각을 거부 (defrag보다 앞 priority −450에서).

## 4. 실습 A — 커널의 자기방어 관찰

```sh
docker exec clab-13-tunnel-mtu-vtep1 ip link show vxlan100 | grep -o "mtu [0-9]*"
docker exec clab-13-tunnel-mtu-vtep2 ip link show vxlan100 | grep -o "mtu [0-9]*"
docker exec clab-13-tunnel-mtu-vtep1 ip link set vxlan100 mtu 1500   # 초과 설정 시도
```
✅ 실측:
```
vtep1: mtu 1450     ← 1500 − 50, 자동
vtep2: mtu 1350     ← 1400 − 50: 협곡이 "자기 링크"라서 안다!
mtu 1500 설정 → RTNETLINK answers: Invalid argument   ← 커널이 거부까지 해준다
```
**해설**: 커널은 성실하다 — 자기가 아는 범위에서는. **비대칭(1450 vs 1350)이 이미 힌트다:**
vtep1의 1450은 "경로"가 아니라 "자기 링크" 기준의 숫자일 뿐이다.

## 5. 실습 B — 증상: 크기가 가르는 운명

```sh
docker exec clab-13-tunnel-mtu-vtep1 ping -M dont -c2 -s 1300 192.168.100.2
docker exec clab-13-tunnel-mtu-vtep1 ping -M dont -c2 -s 1400 192.168.100.2
```
✅ 실측:
```
-s 1300 (outer 1378 ≤ 1400) → 0% packet loss
-s 1400 (outer 1478 > 1400) → 100% packet loss    ← 12장의 지문이 오버레이에서 재현
```

## 6. 실습 C — 와이어의 진실: 숨은 단편화

```sh
docker exec clab-13-tunnel-mtu-r1 tcpdump -nli eth2 src host 10.13.1.1   # 협곡 쪽 와이어
# (다른 터미널에서 -s 1400 ping)
```
✅ 실측:
```
IP 10.13.1.1.46483 > 10.13.2.1.4789: VXLAN, vni 100
IP [total length 1428 > length 1346] (invalid) ... ICMP echo request   ← 선두 조각 (잘려 있다!)
IP 10.13.1.1 > 10.13.2.1: ip-proto-17                                   ← 비선두 조각 (L4 헤더 없음!)
```
**해설**: r1이 outer 1478을 협곡(1400)에 맞춰 두 조각으로 쪼갰다. 두 번째 조각을 보라 —
포트도 VXLAN 표식도 없는 **정체불명의 `ip-proto-17` 파편**이다. 방화벽이 이걸 버리는 이유가
바로 이 모습 때문이고(검사 불가), vtep2의 조각 거부 규칙이 정확히 이걸 버려서
재조립이 영원히 완성되지 않는다. **에러는 어디에도 없다.**

## 7. 한 줄 수정 — 경로 기준으로 오버레이를 줄인다

```sh
docker exec clab-13-tunnel-mtu-vtep1 ip link set vxlan100 mtu 1350   # 경로 최솟값(1400) − 50
```
✅ **성공 판정** (실측): `-s 1400 ping → 0% packet loss` (3회 연속 재현 확인)
**원리**: 이제 큰 inner는 **오버레이 층에서** 나뉘어 outer가 조각 없이 협곡을 통과한다.
(TCP라면 MSS가 1310으로 협상되어 아예 조각날 일이 없다 — MSS clamp도 같은 효과)

## 8. 관찰의 함정 (정직 박스) — 가상 랩과 물리망의 차이
이 랩(veth)에서 **iperf3 TCP 대량 전송은 고장 상태에서도 살아남을 수 있다** — 가상
인터페이스는 GSO(거대 세그먼트를 쪼개지 않고 통째로 전달)가 MTU 검사를 우회하기 때문.
물리 NIC의 세계에서는 어림없는 일이다. **"랩에서 재현 안 되는데요"가 무죄 증명이 아닌 이유** —
관찰 도구와 환경의 특성이 결과를 바꾼다. (그래서 이 장의 판정은 단일 패킷 ping을 쓴다.)

## 9. 정리 / 교훈
- **커널의 자동 MTU는 "자기 링크"의 세금만 안다.** 경로의 협곡은 운영자가 설계에 반영해야 한다
  — 오버레이 MTU = **경로 전체 최솟값 − 오버헤드(VXLAN 50B)**.
- 단편화는 침묵의 임시방편이다. 동작하는 동안엔 보이지 않고, 조각 거부를 만나면 "큰 것만" 죽는다.
- 진단 축: 양쪽 vxlan MTU 대조(비대칭 = 힌트) → 크기 이등분 ping → 협곡 쪽 와이어에서 조각 확인.
- 12장과 같은 병의 같은 치료: 경로를 아는 값으로 줄이거나(MTU), TCP라면 MSS clamp.

## 10. 치트시트
| 목적 | 명령 |
|---|---|
| 오버레이 MTU 확인 | `ip link show vxlan100` |
| 조각 관찰 | `tcpdump -nli <if>` — `ip-proto-17`/`offset` 파편 |
| 크기 이등분 탐색 | `ping -M dont -s <크기>` 를 크기 바꿔가며 |
| 수정 | `ip link set vxlan100 mtu <경로최솟값-50>` |
