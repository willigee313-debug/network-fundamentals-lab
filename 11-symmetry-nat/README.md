# 11장. 경로 대칭성 & 상태 + NAT의 소스 재작성 — "포워드는 되는데 리턴이 죽는다"

> 08장(증상 지문) + 09장(상태 테이블) + 10장(소스 재작성)이 합성되는 장이다.
> 시나리오: 라우터의 라우트 **한 줄**이 리턴 트래픽만 NAT 장비로 흘려보낸다. 포워드는 완벽하고,
> 서버도 완벽한데, 클라이언트는 영원히 타임아웃 — 실무에서 며칠을 잡아먹는 부류의 장애다.

## 0. 학습 목표
- **경로 비대칭**(forward ≠ return)이 **헤더 재작성/상태 장비**와 만나면 왜 치명적인지
- 결정적 지문: **"SYN-ACK가 내가 접속한 IP가 아닌 곳에서 온다"** 를 tcpdump로 잡기
- 다지점 캡처(cli/nat 전후)로 패킷 여정을 재구성하는 법
- 심화: 같은 비대칭이라도 장비 특성(무재작성/stateless/stateful)에 따라 증상이 3종으로 갈림

## 1. 개념

### 1-1. 두 가지 원리의 충돌
1. **왕복은 독립된 결정이다** (04장): 각 라우터가 따로 정한다 → 비대칭은 언제든 생길 수 있다.
2. **NAT/상태 장비는 왕복을 다 봐야 한다** (09·10장): 소스를 바꾸거나(NAT) 상태를 조회(FW)하므로.

→ 리턴만 NAT를 "스치면": NAT는 처음 보는 패킷의 소스를 성실히 재작성하고,
클라이언트는 **접속한 적 없는 IP에서 온 SYN-ACK**를 받아 커널 수준에서 버린다(RST).

### 1-2. 왜 이 장애가 교묘한가
- 서버 쪽에서 보면: 요청 수신 ✓, 응답 발신 ✓ — **서버는 무죄로 보인다.**
- 클라 쪽에서 보면: 그냥 타임아웃 — 08장의 "조용한 실패" 지문.
- 원인은 중간 어느 라우터의 **라우트 한 줄** — 어느 쪽 팀의 시야에도 잘 안 걸린다.
- 열쇠는 단 하나: **클라에서 tcpdump로 SYN-ACK의 소스를 보는 것.**

## 2. 토폴로지
```
   cli(10.11.1.10) ── edge ─────── srtr ── srv(10.11.2.10:443)
                        \          /
                         \        /          전송망: edge↔srtr 10.11.0.0/30
                          ─ nat ─                   srtr↔nat 10.11.3.0/30
                        (10.11.4.1)                 nat↔edge 10.11.4.0/30
```
**장전된 고장**: srtr의 라우트 `10.11.1.0/24 via nat` — **리턴만** nat를 경유한다.
(포워드 cli→edge→srtr→srv는 nat를 거치지 않음에 주목)

> **구현 노트**: nat의 재작성은 nft **stateless** 룰이다. 리눅스 conntrack NAT(masquerade)는
> "SYN 없이 온 SYN-ACK"를 INVALID로 판정해 **NAT하지 않으므로** 이 장애가 그대로 재현되지
> 않는다(실습 D-2에서 직접 확인). 실제 장애 장비들이 보인 "지나가는 리턴 전부 재작성"을 모사한 것.

## 4. 실습 A — 증상
```sh
docker exec clab-11-symmetry-nat-cli bash -c "time nc -zv -w 5 10.11.2.10 443"
# → timed out ... real 0m5.008s        (실측)
```
08장의 분류로는 "타임아웃 = SYN이 조용히 소실"이어야 한다. 정말 그런지 캡처해 보자.

## 5. 실습 B — 결정적 장면
```sh
docker exec clab-11-symmetry-nat-cli tcpdump -nli eth1 tcp port 443   # 켜두고 다시 nc
```
✅ 실측:
```
10.11.1.10.51002 > 10.11.2.10.443: Flags [S]        ← ① 서버(10.11.2.10)로 SYN
10.11.4.1.443   > 10.11.1.10.51002: Flags [S.]      ← ② 응답이 왔다... 10.11.4.1?!
10.11.1.10.51002 > 10.11.4.1.443:  Flags [R]        ← ③ 커널: "모르는 상대" → RST
10.11.1.10.51002 > 10.11.2.10.443: Flags [S]        ← ④ 원래 시도는 SYN 재전송 → 타임아웃
```
**해설**: 타임아웃인데 **무응답이 아니다!** SYN-ACK는 오고 있다 — 다만 **접속한 적 없는
IP(10.11.4.1 = nat)** 에서. seq/ack 번호를 보면 분명히 내 SYN에 대한 응답인데, 소스가 다르니
커널은 소켓 매칭에 실패하고 버린다. **08장의 지문표에 없던 네 번째 지문**: "타임아웃 +
엉뚱한 소스의 SYN-ACK" = **비대칭 + 재작성**.

## 6. 실습 C — 여정 재구성 (다지점 캡처)

**① 라우팅 결정 확인 — 범인은 srtr의 한 줄**
```sh
docker exec clab-11-symmetry-nat-srtr ip route get 10.11.1.10
# 10.11.1.10 via 10.11.3.2 dev eth3    ← 클라 대역 리턴을 nat(10.11.3.2)로!   (실측)
```

**② nat 통과 전/후 — 재작성의 현장** (실측, 같은 SYN-ACK 8µs 간격):
```
[nat eth1 유입]  10.11.2.10.443 > 10.11.1.10.39170: Flags [S.]   ← 소스 = srv (원본)
[nat eth2 유출]  10.11.4.1.443  > 10.11.1.10.39170: Flags [S.]   ← 소스 = nat (재작성됨!)
```
같은 seq의 패킷이 nat를 지나며 소스만 바뀌었다. 여정 전체:
```
SYN:      cli → edge → srtr → srv                    (nat 안 거침, 정상)
SYN-ACK:  srv → srtr → nat(재작성!) → edge → cli(drop)
```

## 7. 한 줄 수정
```sh
docker exec clab-11-symmetry-nat-srtr ip route replace 10.11.1.0/24 via 10.11.0.1
```
✅ **성공 판정** (실측):
```
echo hi | nc 10.11.2.10 443  →  pong   (real 0m0.003s)
cli 캡처: 10.11.2.10.443 > ... Flags [S.]    ← SYN-ACK 소스가 서버 본인!
```

## 8. 실습 D(심화) — 같은 비대칭, 세 가지 운명

비대칭 라우트를 그대로 두고 **nat의 동작만** 바꿔가며 비교한다 (전부 실측):

**D-1. 재작성 제거 (nat = 순수 라우터)**
```sh
docker exec clab-11-symmetry-nat-srtr ip route replace 10.11.1.0/24 via 10.11.3.2  # 비대칭 복원
docker exec clab-11-symmetry-nat-nat  nft flush table ip rewrite                    # 재작성 제거
# → echo hi | nc ... → pong (0.001s 성공!)
```
**비대칭인데 멀쩡하다.** 소스가 보존되니 클라는 경로 따위 신경 쓰지 않는다.
→ **문제는 비대칭 자체가 아니라, 비대칭 + (재작성 또는 상태 검사)다.**

**D-2. conntrack masquerade로 교체 (전형적 리눅스 NAT)**
```sh
docker exec clab-11-symmetry-nat-nat iptables -t nat -A POSTROUTING -o eth2 -j MASQUERADE
```
✅ 실측 — 가장 교묘한 놈:
```
nc -zv (connect만)     → succeeded! (0.001s)     ← 헬스체크는 통과한다!
echo hi | nc (데이터)   → 수신: []                ← pong이 영원히 안 옴
```
**해설**: conntrack은 midstream SYN-ACK를 INVALID로 보고 **NAT 없이 통과**시킨다(소스 보존
→ 핸드셰이크 성공). 그런데 **그 다음 패킷부터** 픽업해 재작성한다 → 서버의 데이터만 엉뚱한
소스로 도착 → 버려짐. 결과: **"연결은 되는데 데이터가 안 와요"** — 포트 체크·간단한 헬스체크는
전부 통과하면서 실 서비스만 죽는, 잡기 힘든 변종. 상태형 장비의 상태 판정이 증상을 조각낸다.

| nat의 동작 | 증상 |
|---|---|
| 없음 (순수 라우터) | 정상 동작 |
| stateless 재작성 (기본 장전) | connect부터 타임아웃 + "엉뚱한 소스의 SYN-ACK" |
| stateful masquerade | **connect 성공, 데이터만 사망** |

## 9. 정리 / 교훈
- **포워드가 되는데 리턴이 안 되면: 경로 대칭성과 헤더 재작성을 의심하라.**
- 결정적 진단은 **클라이언트에서 SYN-ACK의 소스 IP를 보는 것** — 접속한 IP와 다르면 종결.
- 서버 무죄 + 클라 타임아웃 + 중간 어딘가의 라우트 한 줄 — 이 패턴을 기억하라.
- 상태형/재작성 장비(NAT·방화벽·LB)는 **왕복이 같은 장비를 지나도록 설계**하는 것이 원칙.
- 증상이 "전부 죽음"이 아니라 "연결만 되고 데이터 사망"이면 stateful 장비의 부분 픽업을 의심.

## 10. 치트시트
| 목적 | 명령 |
|---|---|
| SYN-ACK 소스 확인(핵심) | `tcpdump -nli eth1 tcp port <p>` — S. 패킷의 src |
| 라우터의 리턴 결정 | `ip route get <클라IP>` (각 라우터에서) |
| 다지점 추적 | 장비 유입/유출 인터페이스에 tcpdump 쌍으로 |
| stateless 재작성(모사용) | `nft ... ip saddr set <IP>` |
