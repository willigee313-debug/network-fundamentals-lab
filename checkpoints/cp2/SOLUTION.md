# CP-2 해설 — ⚠️ 스포일러! 스스로 풀기 전엔 열지 말 것

## 구조
- **진짜 원인**: srtr의 `10.92.1.0/24 via 10.92.3.2(nat)` — 리턴만 nat 경유(11장 비대칭)
  + nat의 소스 재작성 → cli가 SYN-ACK를 버림.
- **미끼**: edge의 `tcp dport 8080 drop` 규칙 — 눈에 확 띄지만 서비스는 **443**이라 무관.

## 모범 진단 경로 (실측 출력)

### 1단계 — 증상 지문
```
nc -zv → timed out (4초)      ← 조용한 실패 계열 (08장 분류)
```
서버팀 주장("응답 보냈다")과 모순 → 08장 표에서 "리턴 안 옴/소스 불일치" 가지로.

### 2단계 — 결정적 증거: cli에서 tcpdump
```
10.92.4.1.443  > 10.92.1.10.34474: Flags [S.]   ← SYN-ACK가 오긴 온다...
10.92.1.10.34474 > 10.92.4.1.443:  Flags [R]    ← 그런데 소스가 10.92.4.1?!
```
**접속한 곳은 10.92.2.10인데 응답은 10.92.4.1에서** — 11장의 지문 그대로.
서버팀 무죄가 입증됐다(응답은 진짜 발신됨). 문제는 돌아오는 길 위의 재작성.

### 3단계 — 미끼 걸러내기
```
edge$ nft list ruleset →  tcp dport 8080 drop
```
수상해 보이지만 **서비스 포트는 443** — 이 규칙은 이 장애와 무관하다. 증거 없이
이걸 지웠다면 감점. (지워도 증상이 안 변하는 것까지 확인했다면 무죄 증명으로 가점)

### 4단계 — 10.92.4.1이 누군지 역추적 → 라우팅 결정 조사
10.92.4.1 = nat의 인터페이스. 리턴 경로에 nat이 끼어 있다는 뜻 → 각 라우터에서:
```
srtr$ ip route get 10.92.1.10
10.92.1.10 via 10.92.3.2 dev eth3      ← 클라 대역 리턴을 nat로 보내는 한 줄 (범인)
```

### 수정 (한 줄)
```sh
docker exec clab-cp2-srtr ip route replace 10.92.1.0/24 via 10.92.0.1
```
```
echo hi | nc 10.92.2.10 443  →  cp2-ok     ← 완치 (실측)
```

## 채점 기준
| 항목 | 통과 |
|---|---|
| cli에서 **SYN-ACK의 소스**를 캡처로 확인했나 | 이것 없이는 추측 |
| 미끼(8080 drop)에 낚여 엉뚱한 수리를 했나 | 증거 기반 무죄 처리 |
| "서버는 응답했다"는 주장을 검증/활용했나 | 다지점 관점 통합 |
| 수정이 정확히 한 줄(라우트)이었나 | 원인 특정의 정밀도 |
