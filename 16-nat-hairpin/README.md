# 16장. NAT 심화 — 헤어핀: "밖에서는 되는데, 안에서 공인 IP로는 안 돼요"

> 10장에서 DNAT 포트 공개를 배웠고, 11장에서 "왕복이 NAT를 함께 지나야 한다"를 배웠다.
> 이 장은 그 둘의 교차점에서 터지는 실무 단골: **내부 클라이언트가 자기네 공인 IP로 접속**
> 하면(헤어핀), 외부에선 멀쩡한 서비스가 내부에서만 타임아웃 난다. 원인은 이번에도 대칭성 —
> 단, 11장과 반대로 **리턴이 NAT를 "건너뛰어서"** 문제다.

## 0. 학습 목표
- **헤어핀(NAT loopback)**: 내부→공인 IP→(DNAT)→내부 서버로 꺾이는 경로
- 왜 DNAT만으로는 부족한가 — 응답이 NAT를 우회하는 순간 세션이 깨진다
- 결정적 지문: **SYN-ACK가 "주소도 포트도 다른 곳"에서 온다**
- 처방: 헤어핀 구간 한정 SNAT(masquerade) — 소스를 희생해 왕복을 강제

---

## 1. 개념

### 1-1. 헤어핀 경로의 해부
```
정상(외부):  ext → nat(공인:8080 → DNAT → srv:80) → srv → nat(역번역) → ext   ✓ 왕복이 nat 경유

헤어핀(내부): cli → nat(DNAT) → srv ─┐
                  ✗ ←──────────────┘  srv가 소스(cli 사설 IP)를 보고 "어? 같은 동네네"
                                       → nat을 건너뛰고 L2로 직접 응답!
```
- DNAT는 **목적지만** 바꾼다(10장) — 소스는 cli의 사설 IP 그대로 srv에 도착한다.
- srv 입장에서 cli는 같은 서브넷 이웃 → 응답은 게이트웨이(nat)를 거치지 않고 직행.
- cli의 소켓은 `공인IP:8080`을 기다리는데 도착한 건 `srv실주소:80` → 커널이 폐기. **비대칭의 변주.**

### 1-2. 11장과의 대구(對句)
| | 11장 | 16장(헤어핀) |
|---|---|---|
| 고장 | 리턴이 NAT를 **불필요하게 경유** | 리턴이 NAT를 **필요한데 건너뜀** |
| 공통 원리 | **번역이 개입한 세션의 왕복은 같은 번역기를 지나야 한다** | ← 동일 |

## 2. 토폴로지
```
  cli(.10) ─┐
  srv(.20) ─┼─ sw ── nat(내부 .1 / "공인" 10.16.99.1)
            │        └ DNAT :8080 → srv:80 (장전됨) / 헤어핀 SNAT 없음 (고장)
  내부망 10.16.1.0/24
```

## 4. 실습 A — 증상

```sh
docker exec clab-16-nat-hairpin-cli bash -c "time curl -s -m 4 http://10.16.99.1:8080/"
# → 타임아웃, real 0m4.009s     (실측)
```

## 5. 실습 B — 결정적 지문 (cli에서 캡처)

```sh
docker exec clab-16-nat-hairpin-cli tcpdump -nli eth1 'tcp port 8080 or tcp port 80'
```
✅ 실측:
```
10.16.1.10.33916 > 10.16.99.1.8080: Flags [S]      ← 공인 IP:8080으로 접속 시도
10.16.1.20.80   > 10.16.1.10.33916: Flags [S.]     ← 응답이 srv 실주소:80에서?!
10.16.1.10.33916 > 10.16.1.20.80:  Flags [R]       ← 커널: "모르는 상대" → RST
```
**해설**: 11장에선 SYN-ACK의 **주소**가 달랐다. 여기선 **주소와 포트가 둘 다** 다르다
(8080→80 DNAT 흔적까지 노출). 응답 자체는 왔으므로 서버 무죄 — **경로가 번역기를 우회**한 것.

## 6. 실습 C — srv 쪽 교차 검증

```sh
docker exec clab-16-nat-hairpin-srv tcpdump -nli eth1 tcp port 80
```
✅ 실측:
```
10.16.1.10.34474 > 10.16.1.20.80: Flags [S]        ← DNAT는 동작했다 (dst가 srv:80)
10.16.1.20.80 > 10.16.1.10.34474: Flags [S.]       ← 그리고 소스=cli 사설 IP를 보고 "직접" 응답
```
**해설**: srv에 도착한 소스가 **cli의 사설 IP 그대로**라는 게 문제의 씨앗이다.
같은 서브넷 소스에게 게이트웨이를 경유할 이유가 없으니(04장 원리) 직행했고, 번역은 미완성이 됐다.

## 7. 한 줄 수정 — 헤어핀 구간만 소스를 빌린다

```sh
docker exec clab-16-nat-hairpin-nat iptables -t nat -A POSTROUTING \
  -o eth1 -s 10.16.1.0/24 -d 10.16.1.20 -p tcp --dport 80 -j MASQUERADE
```
✅ **성공 판정** (실측):
```
curl http://10.16.99.1:8080/ → pong-hairpin (0.004s)
srv가 보는 소스: 10.16.1.1(nat)     ← 이제 srv는 nat에게 응답 → 역번역 완성
```
**해설**: 헤어핀 트래픽에 한해 소스를 nat으로 바꿔 **srv의 응답이 반드시 nat을 지나게 강제**했다.
대가는 10장에서 배운 그것 — **srv는 내부 클라의 진짜 IP를 모른다** (접속 로그가 전부 nat IP).
`-s/-d/--dport`로 범위를 좁힌 이유: 대가를 치르는 트래픽을 최소화하기 위해.

### 콜아웃 — 실무 처방 3종
1. **헤어핀 SNAT** (이 장): 어디서나 같은 공인 IP 사용 가능, 단 서버가 내부 소스를 잃음.
2. **스플릿 DNS**: 내부에선 이름이 사설 IP로 풀리게(14장) — NAT 우회, 소스 보존. 단 DNS 이원 관리.
3. **embedded-IP 프로토콜 경고**: FTP active/SIP처럼 **페이로드에 IP를 적는** 프로토콜은
   헤더만 바꾸는 NAT와 근본적으로 상성이 나쁘다(ALG 필요). — NAT가 만능이 아닌 이유.

## 8. 정리 / 교훈
- 헤어핀 = DNAT + **우회 리턴**. 지문: SYN-ACK의 주소·포트가 접속처와 다름.
- 11장과 한 문장으로 통합: **번역이 개입한 세션은 왕복이 같은 번역기를 지나야 한다** —
  경유가 과해도(11), 모자라도(16) 깨진다.
- "밖에서는 되는데 안에서는 안 됨" 티켓 → 헤어핀/스플릿 DNS부터 의심.

## 9. 치트시트
| 목적 | 명령 |
|---|---|
| 헤어핀 SNAT | `iptables -t nat -A POSTROUTING -s <내부망> -d <서버> -p tcp --dport <p> -j MASQUERADE` |
| NAT 규칙/카운터 | `iptables -t nat -vnL` |
| 번역표 | `conntrack -L` |
